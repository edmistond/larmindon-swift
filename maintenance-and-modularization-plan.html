Engineering plan / September 2026

Cleaning up
the landscaping.

A maintenance and modularization plan for Larmindon, preparing the audio pipeline and speech-provider boundaries for what comes next.

Prepared 18 September 2026 Status 01A–01C implemented Audited revision fe9eeb1

The recommendation

A focused maintenance pass.

The codebase is still manageable. Its highest maintenance costs are concentrated around audio capture, session orchestration, and provider construction. Those are also the areas that custom audio processing and a second server backend would expand.

Preserve the useful foundations: small caption models, actor-isolated networking and diagnostics, an injectable WebSocket transport, explicit interruption policies, and regression tests for restart and scrolling behavior.

Recommended investment: establish deterministic checks, strengthen failure-path tests, finish the provider abstraction, and consolidate capture. Introduce build-enforced module boundaries after those responsibilities have settled.

Tasks 01A–01C now provide a local check workflow, consistent formatting, and a Swift compiler warning gate; CI and release automation are deferred. The remaining phases are proposals. Task identifiers make individual changes easy to request, review, and roll back. Proposed type names describe responsibilities; they are not a requirement to introduce a framework or a particular dependency.

Existing behavior is the baseline. Structural changes and intentional behavior fixes should be separate changes, with separate evidence. DSP algorithms, Azure integration, and speech-quality claims remain follow-on work.

Behavior to preserve

The compatibility contract.

  • Saved configuration survives. Preserve preference keys, serialized enum values, defaults, theme migration, and Keychain service/account identifiers. Add explicit migration tests when a representation changes.
  • Captions retain their meaning. Preserve finalized order, volatile replacement, speaker boundaries, transcript export, scroll position, and clear behavior.
  • Start and Stop remain predictable. Preserve generation guards, local teardown ordering, bounded provider finishing, and rejection of stale events from retired providers.
  • Launchers remain idle-only. A widget launch must not replace a running, starting, stopping, or interrupted session. A consumed tap must not queue a later restart.
  • Interruptions respect user intent. A deliberate Stop must disarm recovery. Route release must never tear down the replacement session.
  • Audio behavior stays observable. Preserve requested versus active voice-processing state, selected-input behavior, buffer configuration, and the different meanings of Apple and server activity meters.
  • Provider choice stays explicit. Preserve the existing Soniox default in server mode. Do not silently fall back to a different provider or send audio to another service.
  • Public surfaces remain compatible. Keep the app-facing LarmindonKit API and existing initializers through adapters or overloads while implementation moves behind them.

A refactor cannot establish “no breaking changes” by inspection alone. Each work package needs a scoped comparison against these behaviors. Changes to capture ownership also require a physical-device pass before claiming parity.

Phase 01Tooling & baseline

Establish deterministic quality gates.

Prerequisites: none. Start here; keep tooling and mechanical formatting separate.

01A · Reproducible checks · Implemented

One local command, with explicit setup.

./scripts/check.sh is the full check entry point. One toolchain file pins Xcode 27.0 (27A266a), Swift 6.4, Tuist 4.200.1, SwiftLint 0.65.1, and the iOS 26.5 simulator runtime. The bundled formatter is identified by the Xcode pin; its configuration and enforcement were added in 01C.

The command regenerates the Tuist workspace, runs package tests on macOS and the CoreTests scheme on iOS Simulator, and builds both apps and the widget without signing. swift test alone omits the app entry point and widget and does not exercise iOS-only tests. The runner also exercises its own failure-path regression tests.

Start with the README setup instructions. ./scripts/check.sh setup explicitly installs a checksum-verified linter under ignored .build/ storage. Routine checks fail for missing or mismatched tools, missing source groups, invalid lint configuration, or failed build/test commands. They never autofix, install tools, call paid providers, or request credentials. Git-visible inputs are checked for changes after the run.

Use ./scripts/check.sh lint for quick feedback; test and build select focused subsets. Per-run reports and logs live under .build/checks/. CI checkout jobs, signing, and distribution automation are deferred; the supported near-term workflow is cloning the repository and following these local instructions.

Acceptance: the documented local command runs with pinned tools; app/widget build failures are visible; checks do not change source inputs. A simulator UDID can be selected explicitly, but the runtime cannot silently drift to “latest.”

Original 01A verification, 18 September 2026: 12 check-runner tests, 136 macOS tests, 146 iOS simulator tests, and both app/widget builds passed, including in a clean temporary worktree. The source-input integrity check passed. 01C extends this workflow with formatting and Swift warnings-as-errors.

01B · Lint and complexity policy · Implemented

Gate useful signals; record existing debt.

The gate configuration uses an explicit rule list: force casts/tries, duplicate conditions and dictionary keys, unused optional bindings, unhandled throwing tasks, invalid or unnecessary suppression commands, and cyclomatic complexity. It scans app, framework, widget, test, and build-manifest Swift sources. The audit’s incompatible concurrency-annotation rule remains excluded.

The reviewed baseline originally contained the four complexity hotspots listed above, allowing the tooling change to preserve startup behavior. Phase 02 retires the Soniox exception after separating its event, audio-send, and ping loops; three exceptions remain. No correctness-rule exceptions were needed. Keep baseline changes visible in review; the runner never regenerates it. Retire existing entries as their functions are simplified.

New complexity findings above 10 fail because the gate uses --strict. Above 20 is an error and should require decomposition before adding more responsibility. Exceptions should be narrow and explain the domain reason. A separate metrics pass ignores the baseline and reports complexity, function/type/file length, and nesting; length and nesting remain advisory.

A baseline is a suppression mechanism, not proof that an existing function has not become more complicated. Inspect changes to baselined lifecycle code and track its raw score during the refactor. Gate regression tests use disposable source copies to exercise new violations, advisory-only findings, configuration errors, baseline portability, and unchanged source inputs.

Acceptance: deliberately introduced correctness and complexity violations fail; the existing baseline passes; the four measured startup hotspots remain visible in the unfiltered report. Baseline regeneration is an explicit review operation documented in the README.

01C · Formatting, warnings, and documentation · Implemented

Make mechanical maintenance inexpensive.

The formatter configuration sets four-space indentation, a 120-column target, and no extra indentation within conditional-compilation blocks. String-literal reflow and broader style rewrites are disabled. The mechanical sweep is checkpoint b923ad3, separate from test-fixture and check-runner changes.

./scripts/check.sh format performs a read-only formatting check. The same gate runs in lint and the full command, covering production, widget, test, test-host, and manifest sources. Deliberate formatting uses the pinned Xcode's swift-format with the checked-in configuration, as documented in the README.

Local SwiftPM tests now receive -Xswiftc -warnings-as-errors; Xcode tests and app builds receive SWIFT_TREAT_WARNINGS_AS_ERRORS=YES. Swift 6 language checking remains enabled. Other build-tool notices remain visible in the logs. Keep SDK/toolchain upgrades separate so newly introduced diagnostics are attributable.

The deprecated UIWindow(frame:) fallback is removed. The iOS unit-test suite uses a blank test host to provide a real window scene; layout tests retain a fixed viewport and fail clearly if the scene is absent. This host is test infrastructure, with no capture or diagnostics startup.

The README now describes the current transcription modes, theme pairing, implemented voice processing, capture buffer settings, microphone/diagnostics panel, and macOS input routing. Agent instructions use the same local check workflow.

Acceptance: the initial second formatter pass produced no changes; regression checks reject unformatted input without rewriting it and reject an actual Swift compiler warning. The full local command validates the chosen warning policy, existing tests, and app/widget builds.

Validated 18 September 2026: the full local gate passed with 17 runner tests, 136 macOS SwiftPM tests, 146 iOS tests, and macOS/iOS app and widget builds. The 136 macOS tests also passed through Xcode, confirming that the iOS-only host does not break the macOS scheme. Both Xcode test runs reported zero skipped tests. The four complexity exceptions and their measured scores are unchanged.

Phase 02Implemented · 18 September 2026

Protect lifecycle boundaries.

Prerequisites: reuse the Phase 01 checks as they become available. These tasks can proceed independently of formatting.

02A · Capture failure seam

Test cleanup after partial startup.

Implemented: a capture driver and permission seam exercise startup without opening a microphone. Cleanup follows resource ownership, cancels pending startup, and runs once. The regression first failed with zero resource releases, then passed with the fix (ba3c11f). Tests also cover local teardown before route release and replacement isolation.

Introduce the smallest injectable capture-driver boundary needed to simulate acquiring a tap or direct-capture resource and then failing to start. Keep engine-specific behavior in the production implementation.

At audit time, AudioCaptureSession acquired resources before setting isRunning, while stop() returned early if that flag was false. Explicit cleanup could therefore be skipped on a failed start. Clean up according to the resources actually acquired, including repeat Stop and cancellation during startup.

Acceptance: a regression test fails against the current partial-start path and passes with the fix; cleanup happens once; route release follows local capture teardown; a replacement session remains unaffected.

Evidence: AudioCaptureSession.swift, lines 114–132 and 185–203; existing restart tests.

02B · Failure and delivery contracts

Characterize behavior before changing it.

Implemented: Apple transcriber/analyzer errors now emit one terminal .failure, never spoken text; intentional cancellation stays silent (f1fbfcb). Soniox keeps its 64-event bound and permits replacement of partial previews. If a finalized event is evicted, it closes delivery with an explicit error and retires the connection. This overflow policy is recorded in Blinken. Every SQLite read loop now checks step results; a real integer-overflow query proves that failure after a successful row throws.

At audit time, the Apple source emitted some runtime errors as volatile caption text; Soniox emitted .failure, which the session treats as an error. Define the intended common contract and test it. Changing the Apple path to stop on failure is an intentional behavior fix, not a mechanical extraction; keep it in its own change.

Exercise Soniox’s bounded result stream under a delayed consumer. At audit time, it shared one dropping queue between partial and final results. Define how partial updates can be coalesced and how finalized events are preserved or overflow is surfaced. Do not solve this by silently switching every queue to unbounded buffering.

Separately, make diagnostic SQLite reads distinguish SQLITE_DONE from step errors. Use a checked iteration helper and an injected or induced step-error test; a closed-store test alone only exercises statement preparation.

Acceptance: terminal errors cannot be mistaken for spoken text under the chosen contract; delayed-consumer tests account for every finalized event; database read failures are reported rather than appearing as successful partial results.

Evidence: Apple source, lines 225–227 and 272–277; Soniox source, lines 50–55; DiagnosticStore.swift, lines 409–420.

02C · Controlled time and transport failures

Make asynchronous tests deliberate.

Implemented: injected monotonic delays and controlled continuations replace multi-second watchdog waits. Tests cover startup cancellation, recovery backoff, explicit Stop during backoff, mid-stream closure, send failure, missing finish acknowledgement, and retired-provider events. The concrete URLSession transport has a small connection-driver seam plus delegate-bridge tests. Connection identity guards prevent old callbacks and operations from changing a replacement connection.

Inject a clock or narrow scheduling dependency into watchdogs and recovery. Several original tests waited for the production three-second timeout. Advance test time explicitly and use controlled continuations for lifecycle milestones.

Add tests for cancellation at startup boundaries, mid-stream transport closure, send failure, a missing finish acknowledgement, and late events from retired providers. Retain the existing rapid-restart and interruption tests. Add a focused test seam for the concrete URLSession transport rather than assuming fake-transport tests cover its delegate and connection lifecycle.

Acceptance: watchdog/recovery policy tests do not require multi-second real sleeps; cancellation and failure ordering is reproducible; the suite remains independent of microphones, credentials, and external speech services.

Validation: full pinned local gate: formatting and lint, 17 runner tests, macOS SwiftPM tests, iOS simulator tests, and unsigned macOS/iOS app and widget builds. Physical capture, actual Apple recognition, and live Soniox service behavior remain unverified on target hardware.

Phase 03Azure preparation

Complete the provider seams.

Prerequisites: keep lifecycle regression checks green. Prove the boundary with a fake second provider before adding Azure.

03A · Typed session configuration

Resolve settings once for each start.

Create a typed settings snapshot that contains provider selection, capture settings, and recognition settings. Keep those concerns distinguishable within the snapshot: profanity handling is recognition configuration, while buffer size and voice processing concern capture.

Centralize preference keys, defaults, decoding, and migration. Preserve existing storage formats and when each setting takes effect. Avoid adding more independent optional parameters to CaptionSession.start; retain its current entry points as compatibility adapters initially.

Use one credential dependency for session construction, readiness state, and Settings. Distinguish a missing credential from a Keychain access error. Preserve the existing Keychain service and account values.

Acceptance: existing stored values resolve identically; malformed values fall back explicitly; settings displayed and used at startup agree; missing-key and Keychain-error cases are testable without touching personal credentials.

03B · Provider-aware construction

Replace the Soniox-specific startup branch.

Introduce a provider-aware factory and a small audio-input capability such as SessionAudioTranscriptionSource.start(audioFrames:). Use the capability in CaptionSession instead of a concrete Soniox downcast. Keep background finishing a separate capability, because accepting audio and draining safely are different promises.

Thread provider identity through selection, credential lookup, source construction, active state, and diagnostics. The existing provider picker persists a value, but those production paths still hardcode Soniox. Preserve the current default and visible Soniox behavior while completing the wiring.

Keep wire protocols inside adapters. Soniox retains its token decoder, sentence accumulator, configuration, and finish handshake. Azure can choose an SDK or transport independently and keep region/endpoint configuration separate from secrets. Do not generalize the Soniox wire model into a universal network protocol.

Acceptance: a fake second audio-consuming provider starts through the same session path without another concrete-type branch; the selected provider determines credentials and diagnostics; Soniox fixtures and lifecycle tests remain unchanged in outcome.

Evidence: CaptionSession.swift, lines 275–304 and 571–603; PreferencesView.swift, lines 102–107; current source contract.

03C · Shared provider contract tests

Specify the behavior every adapter must provide.

Build reusable scenarios for successful start, missing configuration, partial replacement, final append, empty updates, optional speaker information, terminal failure, cancellation, and bounded finishing. Define whether an adapter is single-use; do not accidentally promise restartability for a source whose streams have finished.

Use normalized events at the app boundary while retaining provider-specific fixtures and rich timing/token information inside the adapter or a separate evaluation event stream. Keep the UI contract small; future evaluation should not have to reconstruct provider timing from rendered strings.

Acceptance: Soniox and the fake second provider pass applicable common scenarios; unsupported capabilities are explicit; app-level code does not inspect provider wire events; normal Stop still preserves the current rapid-restart contract.

Phase 04Highest hardware sensitivity

Unify capture before adding DSP.

Prerequisites: 02A capture lifecycle tests and 03B provider audio-input seam. Keep each ownership change separate from processing changes.

04A · Shared capture drivers

Extract duplication without moving every responsibility at once.

Extract the engine driver, direct macOS capture driver, buffer-copy helpers, and capture telemetry from their duplicated locations. Let both existing paths use adapters over those helpers before transferring all capture ownership to the session.

Preserve device selection, channel handling, format negotiation, requested buffer size, voice-processing fallback, and the existing rule that engine configuration and start remain adjacent with no intervening await. Do not normalize both pipelines to 16 kHz mono just because Soniox currently needs that format.

Once parity is established, make both providers consume the session-owned frame stream. Keep Apple speech-activity meter semantics and Soniox provider-activity semantics separate from capture itself.

Acceptance: both paths use the shared drivers; failure/cancellation tests pass; provider inputs and level behavior match the previous path; physical device and route checks pass before removing the old ownership path.

04B · Frame ownership and provenance

Make gaps and buffer lifetime explicit.

Extend the frame contract with monotonic sequence, sample start/count, capture host time, format identity, and discontinuity information. Document whether a buffer is immutable after publication or uniquely transferred to one consumer. A let reference to a mutable PCM buffer does not itself establish immutability.

Keep queues bounded and expose where drops occur. Distinguish capture loss from converter failure and processing backlog. Sample position should be the canonical audio timeline; diagnostics should not have to infer gaps from wall-clock timestamps.

Audit @unchecked Sendable wrappers at this boundary and record their safety assumptions. If a recorder is later added, use bounded explicit fan-out and account for recording loss without blocking the capture callback.

Acceptance: tests verify ownership, ordering, changing formats, overflow, and discontinuity propagation; metadata addition does not change samples or provider-facing format; drops are observable at the stage where they occur.

04C · Bypass processing worker

Prove the new path before changing the signal.

Introduce a serial processing worker outside the main actor with an explicit bounded handoff. The existing sources create main-actor-inherited tasks that perform synchronous conversion; avoid placing denoising or beamforming inside those loops or inside the real-time capture callback.

Start with an identity processor. Resolve an immutable processing profile at session start that records requested and active Apple voice processing, ordered custom stages, and configuration identity. Keep Apple voice processing selectable and preserve the current default.

Do not add VAD gating, new resampling, denoising, or altered stop-time finalization in this change. A recording/evaluation drain path may eventually need different completion semantics from the responsive UI Stop path; specify that separately.

Acceptance: bypass preserves sample values, order, frame accounting, and conversion inputs; measured latency and drops remain within an agreed baseline; UI work does not execute custom processing; Stop cancels or drains workers according to the documented lifecycle.

Exit condition for this phase: one capture path, explicit ownership and timing, and a verified bypass worker. Improved recognition in noise is a later experimental outcome, not an acceptance claim for this refactor.

Phase 05Boundary enforcement

Make the stable architecture visible.

Prerequisites: extract logical responsibilities first. Small documentation/UI tasks can happen earlier; build-target splitting should follow the stable seams.

05A · Smaller orchestration and views

Give existing responsibilities a home.

Move provider construction, microphone-configuration persistence, and watchdog/recovery scheduling out of CaptionSession. Retain it as the app-facing coordinator and preserve the generation guards and local-stop serialization.

Separate theme/palette presentation from provider and capture configuration in UserPreferences.swift. Extract microphone draft state, diagnostic export, and cohesive view sections where doing so improves ownership and testability. Use CaptionScrollState and AudioInterruptionPolicy as local examples of small policy boundaries.

Acceptance: startup responsibilities can be tested independently; settings and UI behavior remain stable; extraction reduces coupling rather than merely distributing one large type across extension files.

05B · Build-enforced dependencies

Introduce a few targets, when they earn their keep.

Start with a small dependency graph: caption/configuration contracts at the base; audio infrastructure and provider adapters depending on those contracts; orchestration and presentation composing them. Provider adapters should not depend on views or on other providers.

Do not create a package per helper. Keep LarmindonKit as the compatible app-facing surface and move internal implementations gradually. Update Package.swift and Project.swift together, including test resources and the widget’s shared launch-link source.

Add Periphery as a report only after indexing the actual app consumers and relevant platform targets. Review Objective-C/runtime and synthesized-code findings before promoting rules or deleting code. Maintain a short architecture document with dependency direction, capture ownership, and stop/drain semantics.

Acceptance: forbidden dependencies fail to compile; both build descriptions cover the intended files/resources; existing callers continue to build; no runtime behavior is changed by the target split.

Where to begin

The first useful milestone.

Phases 01 and 02 are implemented: deterministic local quality checks, partial-start cleanup, explicit failure and overflow contracts, checked SQLite reads, and controlled lifecycle/transport tests. Physical microphone, interruption, and live-provider validation remain device checks. The next structural milestone is Phase 03; DSP and unified capture remain Phase 04 work.

After that, choose the next boundary according to the upcoming feature:

  • Azure comes first: complete 03A–03C. The proving step is a second fake provider passing through the existing session, before any real service integration.
  • Audio processing comes first: complete the provider audio-input seam, then 04A–04C. The proving step is unchanged output through a single capture path and bypass worker.
  • General maintenance continues: take selected 05A tasks as separate changes. Defer production target splitting until dependency direction is clear.

No new runtime dependency is required merely to begin this plan. The initial maintenance work can use the existing Swift/Xcode toolchain and a pinned development-only linter. Algorithm, SDK, and more extensive tooling dependencies should be evaluated with the feature that needs them.
