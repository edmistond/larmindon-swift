Showing capture health without a live meter

The main screen needs to answer two questions: is audio arriving? and is the recognizer turning it into captions? Today a level meter answers both by moving 20 times a second. This brief proposes a status indicator that changes only when the answer changes, and gives the space it frees back to captions.

Status Proposal, not started Scope iPhone, iPad, macOS main screen Written 2026-09-29

Why now

Battery traces on the iPhone 15 Pro Max (Debug build, Wi‑Fi, 53–55% brightness) showed Larmindon's own cost is mostly the display, not the CPU. Display energy impact rose from 3 to 4 whenever the meter and captions were moving, while CPU impact stayed between 0.1 and 0.7.

Inferred, not isolated. In the silence run the meter and the caption text were both still, so the traces can't split the display cost between them. The likely mechanism is continuous redraws keeping the ProMotion panel from dropping to its lowest refresh rate, but refresh rate wasn't measured directly. Run the A/B in Validate first before sizing the payoff.

Constraints that shape every option

  • Legibility wins ties. Captions are the product. Space freed from controls goes to caption lines, not to more controls.
  • The meter is a debugging instrument. A flat meter is how silent capture gets spotted on hardware. It can move off the main screen but must stay one tap away.
  • Full scrollback stays. Nothing here reduces what the caption stream retains or shows.
  • Status can't rely on color alone. Each state also needs a distinct shape and a text label.
  • No continuous animation. Pulsing, breathing and repeatForever effects, or SF Symbol variable-color effects, redraw every frame. That's worse than the meter.

The signal model

Five states, derived from data the app already has. The indicator redraws only when the state changes.

StateMeaningWhere the data already isEnter after
StoppedNo sessionstore.isRunningImmediately
No audioCapture running, nothing arriving, or only digital silenceThe existing "No audio is arriving" warning in CaptionSession, plus AudioSignalMeasurement.isDigitalSilence2 s
ListeningAudio arriving, recognizer not producing yetCapture callbacks with a non-silent peak1 s
CaptioningAudio arriving and the recognizer is aliveSoniox: the processed-audio position (final_audio_proc_ms) is advancing, which is true even when nobody talks. On-device: a result within the last several seconds.Immediately; drops back to Listening only after about 10 s without activity
StalledAudio flowing but the recognizer has gone quietSoniox: processed-audio position not advancing, or processing lag growing, while audio is being sent. On-device: weaker; see open questions.About 10 s

Stalled is the state that matters most. "Mic fine, captions stopped" is the failure a hard-of-hearing user can't detect by ear. Today it shows only as the meter bar turning grey while still moving.

In the car, road noise keeps the capture signal above silence nearly all the time, so Listening/Captioning mostly means "the mic works" rather than "someone is talking". That's the right meaning for this indicator.

Recommendation

  1. B on iPhone and iPad, F on macOS, both with the five-state indicator and a text label.
  2. D as a complement for Stalled only, since that's the state that needs to interrupt.
  3. Keep the full-rate meter in the Microphone panel (MicrophonePanelView already has one). Long-pressing the status control opens that panel. Optionally add a Settings toggle, "Show live level meter", default off, for hardware test sessions.
  4. Log state transitions as a capture_status_changed diagnostic event. Bundles then show exactly when captions stalled, which pays for itself in debugging.

Implementation notes for the session that builds it

  • Compute the state in CaptionSession from signals it already receives, and publish it as an @Observable property that's written only when it changes. Only the indicator view should read it.
  • Keep audioLevels publishing, but make sure only the Microphone panel observes it. SessionAudioLevelBar already isolates that read from the root body.
  • Hysteresis lives in the state machine, not the view: time thresholds for entering each state, plus a minimum time in a state of about 2 s. Unit-test it with a manual clock, as ManualDelay does elsewhere.
  • Any transition animation is a one-shot crossfade of about 0.2 s. Never a repeating one.
  • The reconnect work adds a "reconnecting" moment. Treat it as a sub-label of Stalled ("Reconnecting…") rather than a sixth ring style.

Validate first

Before building, measure the payoff with a cheap A/B on a Release build:

  1. Temporarily hide SessionAudioLevelBar on the main screen.
  2. Record Instruments power traces with the meter shown and hidden: Soniox active and on-device, each about 3 minutes, at the same brightness, same input and similar speech.
  3. Compare Larmindon's display impact and the system power level (%/hr). If hiding the meter drops display impact back toward the idle 3, the redesign has a measurable battery payoff. If not, it's still worth doing for space, but don't sell it as a battery fix.

Open questions for the notebook

  • Is a text label always shown, or only in Stalled and No audio? Legibility argues for always.
  • On-device stall detection: SpeechAnalyzer only reports when there's speech. Is "signal above speech level for N s with no results" good enough, or should on-device skip Stalled?
  • Should Stalled also trigger a haptic, or the existing failure notification when the app is backgrounded?
  • Clear in the ⋯ menu: it's rarely used and fairly destructive, so moving it is probably good. Confirm.
  • iPhone input selection: a chip that opens the existing picker, or a sheet with routes and the meter together?
  • Stalled thresholds per provider. In last week's bundle Soniox's processing lag had a median of 65 ms and a 95th percentile of about 200 ms, but peaked at 8.6 s. A 10 s threshold clears the worst observed spike; anything much shorter would have raised false alarms.
