Showing capture health without a live meter

The main screen needs to answer two questions: is audio arriving? and is the recognizer turning it into captions? Today a level meter answers both by moving 20 times a second. This brief proposes a status indicator that changes only when the answer changes, and gives the space it frees back to captions.

Status Proposal, not started Scope iPhone, iPad, macOS main screen Written 2026-09-29 Addendum Corner controls, 2026-10-01

Why now

Battery traces on the iPhone 15 Pro Max (Debug build, Wi‑Fi, 53–55% brightness) showed Larmindon's own cost is mostly the display, not the CPU. Display energy impact rose from 3 to 4 whenever the meter and captions were moving, while CPU impact stayed between 0.1 and 0.7.

Inferred, not isolated. In the silence run the meter and the caption text were both still, so the traces can't split the display cost between them. The likely mechanism is continuous redraws keeping the ProMotion panel from dropping to its lowest refresh rate, but refresh rate wasn't measured directly. Run the A/B in Validate first before sizing the payoff.

Constraints that shape every option

  • Legibility wins ties. Captions are the product. Space freed from controls goes to caption lines, not to more controls.
  • The meter is a debugging instrument. A flat meter is how silent capture gets spotted on hardware. It can move off the main screen but must stay one tap away.
  • Full scrollback stays. Nothing here reduces what the caption stream retains or shows.
  • The current input stays visible by name, all the time. Other apps have grabbed the hearing aid as their input while surfacing the choice only briefly. A glance at Larmindon has to confirm which input it's using, not just offer a picker.
  • On-device ↔ Soniox stays one tap away. The segmented control in the top toolbar can be simplified, but quick switching is a feature.
  • Settings and the Microphone panel stay reachable from the main screen. How they're reached is open to rethinking.
  • Status can't rely on color alone. Each state also needs a distinct shape and a text label.
  • No continuous animation. Pulsing, breathing and repeatForever effects, or SF Symbol variable-color effects, redraw every frame. That's worse than the meter.

The signal model

Five states, derived from data the app already has. The indicator redraws only when the state changes.

StateMeaningWhere the data already isEnter after
StoppedNo sessionstore.isRunningImmediately
No audioCapture running, nothing arriving, or only digital silenceThe existing "No audio is arriving" warning in CaptionSession, plus AudioSignalMeasurement.isDigitalSilence2 s
ListeningAudio arriving, recognizer not producing yetCapture callbacks with a non-silent peak1 s
CaptioningAudio arriving and the recognizer is aliveSoniox: the processed-audio position (final_audio_proc_ms) is advancing, which is true even when nobody talks. On-device: a result within the last several seconds.Immediately; drops back to Listening only after about 10 s without activity
StalledAudio flowing but the recognizer has gone quietSoniox: processed-audio position not advancing, or processing lag growing, while audio is being sent. On-device: weaker; see open questions.About 10 s

Stalled is the state that matters most. "Mic fine, captions stopped" is the failure a hard-of-hearing user can't detect by ear. Today it shows only as the meter bar turning grey while still moving.

In the car, road noise keeps the capture signal above silence nearly all the time, so Listening/Captioning mostly means "the mic works" rather than "someone is talking". That's the right meaning for this indicator.

macOS: the toolbar is the natural home

Recommendation

  1. B on iPhone and iPad, F on macOS, both with the five-state indicator and a text label.
  2. D as a complement for Stalled only, since that's the state that needs to interrupt.
  3. Keep the full-rate meter in the Microphone panel (MicrophonePanelView already has one). Long-pressing the status control opens that panel. Optionally add a Settings toggle, "Show live level meter", default off, for hardware test sessions.
  4. Log state transitions as a capture_status_changed diagnostic event. Bundles then show exactly when captions stalled, which pays for itself in debugging.

Implementation notes for the session that builds it

  • Compute the state in CaptionSession from signals it already receives, and publish it as an @Observable property that's written only when it changes. Only the indicator view should read it.
  • Keep audioLevels publishing, but make sure only the Microphone panel observes it. SessionAudioLevelBar already isolates that read from the root body.
  • Hysteresis lives in the state machine, not the view: time thresholds for entering each state, plus a minimum time in a state of about 2 s. Unit-test it with a manual clock, as ManualDelay does elsewhere.
  • Any transition animation is a one-shot crossfade of about 0.2 s. Never a repeating one.
  • The reconnect work adds a "reconnecting" moment. Treat it as a sub-label of Stalled ("Reconnecting…") rather than a sixth ring style.

Validate first

Before building, measure the payoff with a cheap A/B on a Release build:

  1. Temporarily hide SessionAudioLevelBar on the main screen.
  2. Record Instruments power traces with the meter shown and hidden: Soniox active and on-device, each about 3 minutes, at the same brightness, same input and similar speech.
  3. Compare Larmindon's display impact and the system power level (%/hr). If hiding the meter drops display impact back toward the idle 3, the redesign has a measurable battery payoff. If not, it's still worth doing for space, but don't sell it as a battery fix.

Open questions for the notebook

  • Is a text label always shown, or only in Stalled and No audio? Legibility argues for always. Answered in the addendum: always.
  • Simplifying the mode switch: the status label already names the provider ("Soniox"). Could that sub-label become the switch, as a tappable "Soniox ▾" chip, and free the toolbar's center? Or does mode belong in the toolbar where it can't be mistaken for status?
  • On-device stall detection: SpeechAnalyzer only reports when there's speech. Is "signal above speech level for N s with no results" good enough, or should on-device skip Stalled?
  • Should Stalled also trigger a haptic, or the existing failure notification when the app is backgrounded?
  • Clear in the ⋯ menu: it's rarely used and fairly destructive, so moving it is probably good. Confirm. Answered: no. Clear stays on screen at all times; see the addendum.
  • iPhone input selection: a chip that opens the existing picker, or a sheet with routes and the meter together?
  • Stalled thresholds per provider. In last week's bundle Soniox's processing lag had a median of 65 ms and a 95th percentile of about 200 ms, but peaked at 8.6 s. A 10 s threshold clears the worst observed spike; anything much shorter would have raised false alarms.
Addendum · 2026-10-01

Corner controls, from the wireframe

The wireframe keeps B's status ring and the text label, and changes two things the brief didn't consider. Start/Stop and Clear become quarter discs in the two bottom corners, with the input chip between them. Clear stays on screen at all times.

This supersedes parts of the recommendation above.

  • Clear is never hidden, and it's one tap. It doesn't go into a ⋯ menu (B) or the macOS menu bar (F). Clear is how a badly misheard phrase or a stray swear comes off the screen before the people around you read it, so it has to be instant. An always-visible Clear is one of the reasons this app exists.
  • The mode switch goes icon-only, keeping today's rounded capsule style. On-device is SF Symbols iphone.gen3 on iOS and macbook.gen2 on macOS; server is cloud on both. The provider's name moves into the status label ("Captioning · Soniox"), which answers the open question about simplifying the switch.
  • The status label is always shown, centered above the input chip.
  • Toolbar space is held for a future AI control (sparkles.2), which the icon-only switch frees up. It isn't built yet and is left out of the mocks. It's planned to cover speaker identification using Apple's on-device models, plus a way to pick a speaker by hand and name them.

What it looks like

Caption space: the bottom band takes about 15% of the screen height in this mock, against 12% for B and 27% for today's layout. That's roughly one line fewer than B and about three more than today.

The five states, in a corner

Is it practical in SwiftUI?

Yes. Nothing here needs UIKit or private API. A corner button is an ordinary Button whose shape is a custom Shape; the ring is the same arc, stroked.

  1. Quarter disc. A custom Shape centered on the screen corner, about 110 pt in radius. .contentShape limits taps to inside the curve, so the input chip next to it stays tappable.
  2. Status ring. The same arc stroked about 5 pt outside the disc, dashed for No audio via StrokeStyle(dash:). It redraws only when the state changes.
  3. Display corner. The screen's rounded corner clips the tip of the disc. The disc is roughly twice any iPhone's corner radius, so nothing that matters is lost, and the view never needs the device's corner radius, which isn't public API.
  4. Glyph. Sits above the bottom safe-area inset, clear of the corner curve. The disc itself extends below the inset with .ignoresSafeArea, so the whole corner is a target.

A sketch of the shape, not compiled:

/// A quarter disc centered on the bottom corner of its frame.
struct CornerDisc: Shape {
    var edge: HorizontalEdge   // .leading for Start/Stop, .trailing for Clear

    func path(in rect: CGRect) -> Path {
        let leading = edge == .leading
        let corner = CGPoint(x: leading ? rect.minX : rect.maxX, y: rect.maxY)
        var path = Path()
        path.move(to: corner)
        path.addArc(center: corner, radius: min(rect.width, rect.height),
                    startAngle: .degrees(leading ? 270 : 180),
                    endAngle: .degrees(leading ? 360 : 270), clockwise: false)
        path.closeSubpath()
        return path
    }
}

// Pinned to the screen corner, outside the bottom safe area.
StartStopCornerButton(status: session.captureStatus)
    .frame(width: 110, height: 110)
    .contentShape(CornerDisc(edge: .leading))
    .frame(maxWidth: .infinity, maxHeight: .infinity, alignment: .bottomLeading)
    .ignoresSafeArea(edges: .bottom)
  • Home indicator. A tap near the bottom edge still reaches the button; only an upward swipe from the edge goes to the system. The chip sits above the indicator, as in the mocks.
  • Accessibility. The shape is visual only. Each button gets an accessibilityLabel ("Stop captioning", "Clear captions"), and Start/Stop carries the state as its accessibilityValue. The label and chip should scale with Dynamic Type; the discs can stay fixed.
  • iPad and landscape. The discs are a fixed size in points, so on wider screens they stay in the corners and the extra width goes to captions and the label.
  • Liquid Glass, optionally. glassEffect(_:in:) takes a custom shape, so the discs could match other iOS 26 controls. Check it on hardware against the battery work. Glass over a static band should be cheap, but that hasn't been measured.
  • macOS uses the toolbar layout (F), agreed 2026-10-01, with two changes: Clear is a toolbar button, always visible, and the mode switch uses macbook.gen2 / cloud. As on iOS, the status label names the provider ("Captioning · Soniox"), since the switch no longer spells it out.

Suggestions on the wireframe

  • Undo instead of confirm (mock J, agreed 2026-10-01). Clear is used mid-conversation to get a wrong or embarrassing phrase off the screen, so it stays one tap. The corners are also where thumbs rest, and the bottom-right is the one a right thumb reaches most easily, so mis-taps will happen. CaptionStore keeps the cleared lines for a few seconds so Undo can restore them. The toast says only "Captions cleared"; it never shows the removed text again.
  • Clear glyph: SF Symbols clear (or clear.fill), a boxed X. The box separates it from a bare X, which reads as "close" or "dismiss" on iOS. The mocks use the outline version.
  • Keep Clear's red to an edge, not a fill. Red on iOS also means "recording". As an outline, Clear reads as destructive without competing with the amber Stalled ring across the screen. That's how the mocks draw it.
  • Keep the status label in the band rather than moving it up. See mock H: with bottom-anchored captions it's already next to the newest line.

Battery: what this layout does and doesn't change

The battery case for the redesign rests on one thing: removing the continuously moving level meter from the main screen. The corner layout keeps that, and adds nothing that moves continuously.

  • Ring and label redraw only on a state transition, a few times a minute at most, with the same hysteresis as B.
  • Caption text still updates about once a second. That's the product and isn't changed by any layout.
  • The Undo toast appears once and disappears once. Don't give it a countdown bar or a shrinking ring: those animate every frame for five seconds.
  • Button press feedback is a one-shot highlight, like any button.
  • Liquid Glass on the discs is the one unknown; see above.

None of this proves the payoff. It still depends on the meter A/B in Validate first; this layout only makes sure it doesn't give the savings back.

Open from the wireframe

  • What the AI control opens. Answered: speaker identification features, later. Its toolbar slot stays empty for now.
  • A finer-grained Clear: removing just the most recent caption block would take out a misheard phrase without losing the rest of the conversation. A possible second gesture on the same control, such as a long-press; full Clear stays one tap.
  • Whether a left-handed option to swap the corners is worth a setting.
  • Does an icon-only mode switch stay unambiguous on macOS? Answered: yes, with the provider named in the toolbar's status label.
